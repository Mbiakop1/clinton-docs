OCI Resource Naming Standard & Governance Policy

Sep 27, 2026 · @Clinton · Draft v0.9 for architecture board review

1. Executive Summary

The agreed pattern is <org>-<env>-<rgn>-<type>-<app>[-<qual>]-<nn>, and every field has a closed list of
values: org is always cmr; env is dev, uat or prd; rgn is cas (Morocco, Casablanca) or jnb (South Africa,
Johannesburg); type comes from the resource-type catalogue; app from the Application Register; and qual from
the qualifier list for that type. An engineer picks values; nobody invents spellings.

Standard Name (display name of every OCI resource):

<org>-<env>-<region>-<type>-<app>[-<qualifier>]-<nn>

Example: cmr-prd-cas-vm-cbs-ol-01 means the Cameroon entity, production, Casablanca region, a compute VM, the
core banking system, Oracle Linux, instance 01.

The name is deliberately short (≤ 33 characters in practice) and carries only what an engineer needs to act
safely. Everything else (owner, cost centre, criticality, data classification, DR role) goes into mandatory
defined tags enforced by tag defaults and CI/CD. Names are generated by a Terraform naming module, validated
by policy-as-code in the pipeline, and checked nightly across the tenancy.

Because several OCI fields cannot hold the Standard Name (15-character DNS labels, 8-character Oracle DB
names, alphanumeric-only bastions), the standard defines three derived forms computed from the same inputs, so
nobody invents a short name by hand.

Assumptions used throughout (each is revisited in section 27):

-   [ASM-1] Decided: one organisation code, cmr, for every resource.

-   [ASM-2] One production OCI tenancy for the group, segmented by compartments and identity domains. A
    multi-tenancy model does not break this standard; it only changes the top of the compartment tree.

-   [ASM-3] Regions (decided): only two OCI regions are used, cas = Morocco West (Casablanca, af-casablanca-1,
    primary site) and jnb = South Africa Central (Johannesburg, af-johannesburg-1, recovery site).

-   [ASM-4] An application register or CMDB exists (or will) and can own application codes.

-   [ASM-5] Terraform is the primary provisioning path; Console creation is exceptional in production.

Why not Option C, even though it is the cloud-native purist choice: audit logs, SIEM events, alarm messages,
DNS, Data Guard broker output and cost reports frequently show only the display name. A SOC analyst reading
vm-7f3a in a Logging Analytics alert has to pivot to the Console before knowing whether it is production. In a
bank, that delay is a risk.

Why not Option A: it fails OCI hard limits (15-character DNS labels, 8-character Oracle DB names, 12-character
Exadata host prefixes), and descriptive words leak business context.

Challenges to the team's agreed pattern

The team's structure is sound. These are the points we challenge, with the resolution adopted in this
standard.

1.  No region token. In a multi-region DR design, the production database in the primary region and its
    standby in the recovery region would carry identical names. OCIDs contain the region, but people read
    names, not OCIDs. Resolution [REC]: region token mandatory for all regional resources, forbidden for
    global ones.

1.  No country token. The team listed country as a desired attribute but the pattern has no slot for it.
    Resolution (decided): <org> is always cmr, which identifies the organisation and its country.

2.  Environment codes of one or two letters. p and pp are one keystroke apart; d reads as dev or DR; t1/t2 say
    nothing about the purpose of the test. Resolution [REC]: three-letter codes (section 7).

3.  OS or DB type as the fifth field. Useful for compute (Windows vs Linux playbooks differ for SOC and
    patching), but for databases the engine is usually implied by the resource type (a Base Database system is
    always Oracle). Versions (ol8, 19c) become false after in-place upgrades. Resolution [REC]: the field
    becomes a qualifier with a vocabulary per resource type: OS family for compute, workload or topology for
    databases, tier for networking, exposure for load balancers, purpose for buckets, keys and secrets.

4.  No role or component field. Many teams will want web, api, batch. Resolution [REC]: register
    sub-application codes in the application register (for example ibk internet banking, ibkap its API layer)
    instead of adding a sixth token. This keeps the pattern stable and the vocabulary governed.

5.  Where <type> sits. Placing type before application sorts Console lists by type within an environment,
    which suits platform teams. Application teams would prefer app first. Resolution: keep the team's order;
    Console filtering and tags cover the other view. Consistency matters more than the choice.

4. Naming Syntax

Every OCI resource name is built from seven fields in a fixed order. Each field has a closed list of allowed
values, so an engineer only picks values from the lists in sections 6 to 8 and never invents a spelling.

<org>-<env>-<rgn>-<type>-<app>[-<qual>]-<nn>
cmr-prd-cas-vm-cbs-ol-01

4.2 Rules that always apply

-   Lowercase letters a-z, digits 0-9 and hyphens only. No spaces, no underscores, no uppercase, no dots, no
    leading, trailing or double hyphens.

-   Fields are always in the same order and separated by a single hyphen.

-   Global resources have no region field. These are: IAM policies, groups, dynamic groups, identity domains,
    quota policies, budgets, security zones and Cloud Guard targets. Their pattern is
    <org>-<env>-<type>-<app>[-<qual>]-<nn>, for example cmr-prd-pol-cbs-oper-01. Every other resource is
    regional and must include cas or jnb.

-   `nn` starts at 01 for each unique combination of the other fields and goes up by one. Never reuse a number
    while a resource with that name, its backups or its pending deletion still exist. A resource and its DR
    copy in the other region keep the same number.

-   The longest possible name is 33 characters; the validator rejects anything over 40.

4.3 How to build a name in seven steps

1.  org: type cmr.

1.  env: is it production (prd), user acceptance testing (uat) or development (dev)? If it serves both dev and
    uat, use uat. If it serves every environment, use prd.

2.  rgn: which region is selected in the OCI Console (or the Terraform provider) when you create it?
    Casablanca → cas; Johannesburg → jnb. Skip this field if the type is global (4.2).

3.  type: find the resource in the catalogue in section 8 and copy its code.

4.  app: copy the application's code from the Application Register. For shared infrastructure, use the
    platform code listed in section 6.4.

5.  qual: look at the "Qualifier" column in section 8. If it says Required, pick one value from the list named
    there (section 6.5). If it says Optional, add one only if it helps. If it says None, leave it out.

6.  nn: take the next free two-digit number for this exact combination, starting at 01.

Worked example. A production Oracle Linux VM for the core banking system, created in Casablanca: cmr + prd +
cas + vm + cbs + ol + 01 = cmr-prd-cas-vm-cbs-ol-01. Its disaster-recovery twin in Johannesburg is
cmr-prd-jnb-vm-cbs-ol-01.

5. Mandatory vs Optional Components

Six fields are always mandatory; the region field depends on whether the resource is regional or global; the
qualifier depends on the resource type.

  -------------------------------------------------------------------------------------------------------------
  Field           Rule                                              If missing or wrong
  --------------- ------------------------------------------------- -------------------------------------------
  org             Mandatory, always cmr                             Rejected

  env             Mandatory, one of dev, uat, prd                   Rejected

  rgn             Mandatory for regional types, not allowed for     Rejected
                  global types (4.2)                                

  type            Mandatory, from section 8                         Rejected

  app             Mandatory, registered in the Application Register Rejected

  qual            Required, Optional or None, as shown for each     Rejected if required and missing, or
                  type in section 8                                 present when None

  nn              Mandatory, 01–99, including when there is only    Rejected
                  one resource                                      
  -------------------------------------------------------------------------------------------------------------

Why `nn` even when there is only one: one rule for every type, and a predictable name when a second one
appears later.

Why the qualifier is a closed list: a free-text field quickly fills with new, final, temp and personal names.
A closed list per type prevents that and keeps names machine-readable.

6. Controlled Vocabulary

This section lists every value an engineer may type in each field. Anything not listed here is invalid. The
lists live in one versioned registry file in Git, used by the Terraform naming module, the CI validator and
the nightly scan.

One code, one meaning: a code means the same thing wherever it appears. bkp always means backup; sec is never
used because it could mean secret, security or secondary.

6.1 Organisation (org)

  --------------------------------------------------------------------------------------------------------------
  Value             Meaning                                   When to use
  ----------------- ----------------------------------------- --------------------------------------------------
  cmr               The organisation (Cameroon)               Always. Every resource name starts with cmr-.

  --------------------------------------------------------------------------------------------------------------

The field is kept even though it has one value, because names travel outside the tenancy (SIEM, partner SOC
feeds, Oracle support tickets, cost exports) where the prefix identifies the owner, and because it leaves room
for a future entity without renaming anything.

6.2 Environment (env)

Three values: dev, uat, prd. Section 7 explains exactly which one to choose.

6.3 Region (rgn)

  ---------------------------------------------------------------------------------------------------------------
  Value        OCI region               Region identifier (used by        Role           Choose it when
                                        Terraform, CLI)                                  
  ------------ ------------------------ --------------------------------- -------------- ------------------------
  cas          Morocco West             af-casablanca-1                   Primary site   The Console region
               (Casablanca)                                                              selector (or the
                                                                                         Terraform provider) is
                                                                                         set to Casablanca

  jnb          South Africa Central     af-johannesburg-1                 Recovery site  The Console region
               (Johannesburg)                                                            selector (or the
                                                                                         Terraform provider) is
                                                                                         set to Johannesburg

-   The value is the region where the resource physically lives, not the region of its users or of the
    application's primary site. A DR copy in Johannesburg is jnb even though it protects a Casablanca
    workload.

-   cas is our abbreviation for Casablanca. jnb is the same as Oracle's own region key for Johannesburg.

-   No other region may be used. Compartment quotas block the other OCI regions and the validator rejects any
    other value.

-   Global resources (section 4.2) have no region field.

6.4 Application (app)

The application code is 3 to 5 lowercase letters or digits, starting with a letter, assigned by the
Application Register owner. Two examples:

  -------------------------------------------------------------------------------------------------------------
  Value            Application                     Example name
  ---------------- ------------------------------- ------------------------------------------------------------
  cbs              Core Banking System             cmr-prd-cas-vm-cbs-ol-01

  pay              Payments platform               cmr-uat-cas-adb-pay-atp-01
  -------------------------------------------------------------------------------------------------------------

Rules for new application codes:

-   3–5 characters, a-z and 0-9, starting with a letter.

-   A neutral abbreviation of the application's official name. Never a customer name, a confidential project
    codename, a vendor product name or a person's name.

-   Must not be the same as any code in sections 6.1–6.5, 7 or 8.

-   A component of a large application gets its own registered code (for example cbsbt for core banking batch)
    instead of an extra field in the name.

Shared platform codes (proposals for the register owner to confirm): examples in this document use hub
(network hub), net (shared network services), soc (security tooling), obs (observability), kms (key
management), dbp (shared database platform), cicd (DevOps tooling), bkp (backup platform), gold (golden
images) and itg (integration platform).

6.5 Qualifier (qual)

The qualifier says which variant of the resource type this is. The resource type decides whether a qualifier
is Required, Optional or not allowed (None), and which list below applies; section 8 shows this for every
type. Pick exactly one value from that list.

  -------------------------------------------------------------------------------------------------------------
  Value              Meaning                                 Choose it when
  ------------------ --------------------------------------- --------------------------------------------------
  ol                 Oracle Linux                            The image is Oracle Linux, any version

  rhel               Red Hat Enterprise Linux                The image is RHEL, any version

  win                Windows Server                          The image is Windows Server, any version

9. Compartment Naming Standard

Organise compartments tier (prd / npd) → application, with shared security, logging, network, platform and
cyber-recovery compartments beside the tiers, and no separate DR compartment.

Root (tenancy) no resources; break-glass admins only
└── cmr landing zone: tenancy-wide guardrails
├── cmr-soc security tooling, Cloud Guard, SIEM
├── cmr-log log and audit archive
├── cmr-net hub VCNs, DRGs, firewalls, DNS
├── cmr-plat CI/CD, images, observability, Exadata
├── cmr-cyv cyber-recovery vault (own admins)
├── cmr-prd production, both regions, DR included
│ ├── cmr-prd-net production spoke VCNs
│ ├── cmr-prd-cbs core banking
│ └── cmr-prd-pay payments
└── cmr-npd non-production: dev and uat
├── cmr-npd-net non-production spoke VCNs
├── cmr-npd-cbs core banking dev and uat
│ └── cmr-npd-cbs-uat optional UAT-only split
└── cmr-npd-pay payments dev and uat

cmr-prd holds production in both regions, so a DR copy in Johannesburg sits in the same compartment as its
Casablanca primary and inherits the same policies.

9.1 OCI facts that shape the design

-   Compartment names allow letters, numbers, periods, hyphens and underscores, up to 100 characters, and must
    be unique within the parent compartment; they can be renamed (except root). Nesting is limited to six
    levels.

-   Compartments are global: one compartment spans both Casablanca and Johannesburg.

-   IAM policies, budgets, quotas, Security Zones, Cloud Guard targets and tag defaults attach to compartments
    and inherit downwards.

-   Policy statements reference compartments by name or path, and audit events show the compartment name.

9.2 Why this order

  -------------------------------------------------------------------------------------------------------------
  Level          Compartments                                 Reasoning
  -------------- -------------------------------------------- -------------------------------------------------
  L1             cmr                                          Keeps the root empty. Tenancy-wide guardrails
                                                              (Security Zones, quotas, tag defaults, deny-style
                                                              policies) attach here instead of at root, which
                                                              is the OCI Landing Zone pattern.

  L2             cmr-soc, cmr-log, cmr-net, cmr-plat, cmr-cyv Separation of duties: the network team cannot
                                                              alter security tooling; application teams cannot
                                                              touch logs about themselves; the cyber-recovery
                                                              vault has its own administrators, so a
                                                              compromised production admin cannot delete the
                                                              last clean backup.

  L2             cmr-prd, cmr-npd                             Production vs non-production, the most important
                                                              access boundary in a bank. One set of policies
                                                              grants production operators access to all
                                                              production; developers get nothing in cmr-prd.
                                                              Strict Security Zone recipes attach to cmr-prd
                                                              only.

  L3             cmr-prd-cbs, cmr-npd-pay…                    Application: delegation to application teams and
                                                              cost visibility per application. dev and uat
                                                              resources share the npd application compartment
                                                              and are told apart by the env field.

  L4             cmr-npd-cbs-uat                              Optional split, only when uat needs different
                                                              access or data rules from dev.
  -------------------------------------------------------------------------------------------------------------

This uses four of the six levels OCI allows, leaving room to add an entity level later without restructuring.

Alternatives rejected:

-   Application above environment (cbs → prd): gives application teams inherited rights into production by
    default and multiplies production policies by the number of applications.

-   A DR compartment beside production: compartments already span both regions, so it adds nothing
    technically. It duplicates every IAM policy, and a DR drill then fails on a policy difference nobody
    noticed. DR is a region, not a compartment (section 19).

-   A compartment per region: same problem; region is already a property of every regional resource and part
    of its name.

9.3 Compartment naming rule

<parent-name>-<segment>

-   Each compartment name is its full path without the root, joined by hyphens: cmr → cmr-prd → cmr-prd-cbs;
    cmr → cmr-npd → cmr-npd-cbs → cmr-npd-cbs-uat.

-   Allowed segments: tiers prd and npd; functions soc, log, net, plat, cyv; application codes (section 6.4);
    environment codes dev and uat for the optional split.

-   npd is a compartment tier only. It is never an env value in a resource name.

-   No type code, no region, no sequence number, no words such as Production or Shared-Services.

-   Regex: ^cmr(-[a-z][a-z0-9]{1,4}){0,3}$

Why full-path names: OCI only requires uniqueness among siblings, so a tenancy could contain several
compartments named Production. Audit events, Cloud Guard problems, cost reports and IAM error messages would
then show Production with no way to tell which one. A full-path name is unique and self-explanatory wherever
it appears.

  -------------------------------------------------------------------------------------------------------------
  Example                                 Meaning
  --------------------------------------- ---------------------------------------------------------------------
  cmr-net                                 Network hub compartment (both regions)

  cmr-prd-cbs                             Production core banking, primary and DR regions

  cmr-npd-pay                             Non-production payments; dev and uat resources inside, told apart by
                                          the env field

  cmr-npd-cbs-uat                         Optional UAT-only compartment for core banking
  -------------------------------------------------------------------------------------------------------------

Compartment descriptions: mandatory, one sentence stating the purpose and owning team (never a person's name).
Review them for sensitive content (section 17).

12. Networking Naming

Network objects carry the tier as qualifier, so a firewall or flow-log entry tells the SOC which zone traffic
came from, and DNS labels use the Compact Name because OCI caps them at 15 characters and never lets them
change.

12.1 OCI constraints [OCI]

-   VCN and subnet DNS labels: at most 15 alphanumeric characters, starting with a letter, no hyphens or
    underscores, cannot be changed after creation. Subnet labels must be unique within the VCN; VCN labels
    should be unique across the tenancy. Hostnames: up to 63 characters, letters, digits and inner hyphens,
    unique within the subnet, changeable. Source: DNS in your VCN.

-   Display names of VCNs, subnets, gateways, NSGs, security lists and route tables are mutable and
    non-unique.

12.3 DNS zones and records

DNS zone names are real domains, so they follow a domain hierarchy, not the resource pattern [REC]:

<rgn>.<env>.<org>.oci.<corporate-internal-domain>
example: cas.prd.cmr.oci.bank.internal

-   Infrastructure records are region-specific: cmr-prd-cas-vm-cbs-ol-01.cas.prd.cmr.oci.bank.internal.

-   Service records that clients use are region-neutral: cbs-api.prd.cmr.oci.bank.internal, a CNAME that
    points at the active region. Failover changes one record, not every client configuration (section 19).

-   Public zones follow the bank's external domain policy and never reveal environment names for
    non-production (uat.bank.com invites probing); non-production public endpoints should not exist, or sit
    behind generic names [DEC-9].

16. Storage Naming

Bucket names are the most exposed names in OCI: they are unique across the whole tenancy namespace,
case-sensitive, embedded in every API and pre-authenticated request URL, and effectively permanent, so they
get the strictest review.

16.1 OCI constraints [OCI]

-   Bucket names: 1–256 characters; letters, numbers, hyphens, underscores, periods; unique within the
    tenancy's Object Storage namespace (not per region); case-sensitive (accounts-payable and Accounts-Payable
    are different buckets); Oracle advises against confidential information in bucket names. Source: Object
    Storage Buckets.

-   There is no bucket rename in normal operations: renaming means creating a new bucket and copying data,
    which breaks every URL and policy referencing the old name. Treat bucket names as immutable [REC].

19. DR Naming

A DR resource has the same name as its primary, except for the region token. Role (primary or standby) is
never in the name, because roles swap on switchover; the designed site role is a tag; the current role is read
from the service.

19.1 Rules

1.  Same org, env, type, app, qual and nn; different rgn. cmr-prd-cas-adb-pay-atp-01 pairs with
    cmr-prd-jnb-adb-pay-atp-01. A reader sees the pair instantly and a script can join them by stripping the
    region.

1.  Environment stays prd. DR copies of production data are production: same access controls, same monitoring,
    same regulatory scope.

1.  No primary, standby, dr, secondary, backup, new, old in names. After a switchover, a resource called
    ...-standby would be the primary. Engineers under pressure act on names; the name must stay true.

1.  Designed role in a tag: operations.DrSiteRole = primary-site | recovery-site | single-site. This describes
    the architecture (which site is normally active), so it does not change on a drill.

1.  Current role from the source of truth: Data Guard broker, ADB role attribute, Full Stack DR plan state.
    Runbooks query it; nobody infers it from a name.

1.  Same-region standby (Data Guard across availability domains): the peer takes the next sequence
    (...-dbs-cbs-rac-01 and ...-dbs-cbs-rac-02) and both carry the tag operations.DrPair = cbsp1. Availability
    domain and fault domain are never in names: AD labels are mapped per tenancy (your AD-1 is not another
    tenancy's AD-1) and are visible as resource attributes.

1.  Recovery-only resources (exist only in the recovery site, e.g. a DR test jump host) use the recovery
    region token and DrSiteRole = recovery-site.

1.  DR drill clones (snapshot standby clones, test restores) take the next free nn, the tag operations.Purpose
    = dr-test and a mandatory ExpiryDate.

1.  Cyber-recovery copies (immutable, isolated from production admins) live in the cmr-cyv compartment, keep
    the source's org/env/app, and use qual = bkp on buckets: cmr-prd-jnb-bkt-cbs-bkp-02 in cmr-cyv.

1.  Region-neutral service names for clients: applications connect to cbs-api.prd.cmr.oci.bank.internal
    (section 12.3), never to region-specific names, so failover is a DNS change.

20. Multi-Region Naming

Only two regions are used, and the region field is always present in the name of a regional resource and never
in the name of a global one: cas for Morocco West (Casablanca) and jnb for South Africa Central
(Johannesburg).

20.1 Always, or only when necessary?

  -------------------------------------------------------------------------------------------------------------
  Option                                         Assessment
  ---------------------------------------------- --------------------------------------------------------------
  Region only for multi-region workloads         Rejected. "When necessary" is a judgement call, so two
                                                 engineers name the same thing differently. A workload that is
                                                 single-region today gets a DR site next year, and its names
                                                 become inconsistent with the new ones.

  Region always, for regional resources          Adopted. Deterministic (scope is recorded for every type in
                                                 section 8), costs 4 characters, and makes every log line, cost
                                                 row and alarm location-aware.

  Region always, including global resources      Rejected. Compartments, policies and groups span both regions;
                                                 a region field on them would be false.
  -------------------------------------------------------------------------------------------------------------

20.2 Region codes

  --------------------------------------------------------------------------------------------------------------
  Code           OCI region                           Region identifier                     Role
  -------------- ------------------------------------ ------------------------------------- --------------------
  cas            Morocco West (Casablanca)            af-casablanca-1                       Primary site

  jnb            South Africa Central (Johannesburg)  af-johannesburg-1                     Recovery site
  --------------------------------------------------------------------------------------------------------------

-   Readable: both codes are city abbreviations engineers recognise without a lookup.

-   Consistent with OCI where possible: jnb is also Oracle's own region key for Johannesburg.

-   Never typed from memory: the naming module maps the Terraform provider region (af-casablanca-1,
    af-johannesburg-1) to cas or jnb automatically.

-   Rule: the code is the region where the resource physically lives. A DR copy in Johannesburg is jnb, even
    though it protects a Casablanca workload.

20.3 Special cases

  -------------------------------------------------------------------------------------------------------------
  Case                                                     Rule
  -------------------------------------------------------- ----------------------------------------------------
  Resources that span regions (cross-region dashboards,    Use the region where the resource is created (its
  DNS steering policies)                                   home region)

  Home-region-only services (IAM, budgets)                 Global form, no region field

  A third region is approved in the future                 The architecture board assigns a new code in the
                                                           registry; existing names never change

  On-premises data centres                                 Use op1, op2… so a name never leaves doubt about
                                                           whether a resource is in OCI or on-premises

  Data residency                                           Only Casablanca and Johannesburg are approved.
                                                           Compartment quotas set zero quota in every other OCI
                                                           region.
